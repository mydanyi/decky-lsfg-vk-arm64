# ARM64 核心补丁

`patches/0001-arm64-recovery.patch` 基于 [lsfg-vk](https://git.lsfg-vk.dev/lsfg-vk.git) 提交 `0e7a3898c1285b13df8596f2bd2cbb8f85b4383b`，保留已有呈现修正，并加入过载退让、帧节奏恢复和“目标模式”。目标模式按目标 FPS 与实际成功输出做有界预算，使用独立的跨批次呈现调度，并在 fixed/target 实时切换时清理两套策略状态。补丁独立实现调度策略，不包含 MAKO 源码或商业 DLL。

核心沿用上游的 `CC-BY-NC-ND-4.0` 许可，插件外壳的许可不覆盖核心。

在该提交的源码目录中应用补丁后，使用支持 C++20 的 ARM64 工具链构建：

```sh
git apply /path/to/0001-arm64-recovery.patch
cmake -S . -B build -G Ninja \
  -DCMAKE_CXX_COMPILER=aarch64-linux-gnu-g++ \
  -DCMAKE_BUILD_TYPE=Release -DLSFGVK_BUILD_CLI=OFF
cmake --build build --parallel 4
```

将产物 `build/lsfg-vk-layer/liblsfg-vk-layer.so` 作为插件包中的 `bin/liblsfg-vk-v2-arm64.so`。插件界面和核心需要配套更新；旧核心不识别新增的配置字段。

“过载退让与帧节奏恢复”为默认开启的功能。启用后，持续变慢会触发减少实际生成帧数的试探。判断收益时会计入原始帧和生成帧的总输出，而非只看原始帧速度；完全暂停补帧需要总输出至少提升 10%。恢复补帧时，总输出至少提升 5% 才保留新档位。成功退让后清除旧的失败限制，后续负载重新评估。无收益的退让会撤销；设置了基础 FPS 上限时，失败后至少等待 30 秒，并要求连续四个采样窗口的帧周期比失败时进一步增长超过 15%，才重新尝试退让。加载暂停会打断连续恶化计数；相关设置变化会重置控制器。

在 2 倍、3 倍和 4 倍模式下，该开关还会启用提交间隔平滑：先观察原始帧周期，再按实际输出倍率分配提交间隔；过载退让改变实际倍率时，间隔随之调整。每张生成帧分别跟踪完成状态，按测得的原始帧周期等待结果（等待上限 50 毫秒）；第一张就绪后先提交，再在本次呈现调用内按间隔依次提交剩余生成帧和原始帧。全部提交在调用线程上完成，并在返回前报告真实呈现结果；窗口过期、设备丢失等错误不会留到后续帧，生成帧的次优状态和驱动写入的逐交换链结果也会保留。只有中途放弃、最终拷贝尚未提交的批次会保留错误直到交换链重建；最终呈现的可重试错误会在当次返回，后续调用仍可重试。迟到的帧会重新确定后续提交时间，避免集中补交。队列分别同步，呈现调用返回后不会遗留后台队列操作。超时会停止本批额外间隔等待，保留帧的正常呈现，并记录实际就绪次数与提交间隔。若原始帧周期显示总输出损失超过 5%，会逐步缩短间隔，仍变慢时暂时停用平滑，并观察一个采样窗口。若停用后仍然一样慢，则按新场景的帧周期重新学习；若停用确实恢复了吞吐量，则维持停用，直到相关设置改变或停用状态下的帧周期变化超过 15%。加载暂停和临时退让不会单独触发重试。此判据估计的是提交吞吐量，不能保证物理显示间隔或所有场景的性能。

保存的倍率作为上限，基础 FPS 上限保持有效。未设置基础 FPS 上限时，也会定期短暂检查原始帧节奏，以识别被 FIFO 等待掩盖的场景帧率变化。它不能保证所有游戏都获得性能提升。
